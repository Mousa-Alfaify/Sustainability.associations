# مُحرك الاستدامة للجمعيات

منصة تحلل الوضع المالي والتشغيلي للجمعيات الأهلية، ثم تبني لها **محفظة استدامة مالية** من مصادر دخل متكررة تغطي المصاريف التشغيلية (الرواتب، الإيجارات، الأنظمة، الخدمات الإدارية) بدلًا من الاعتماد على التبرعات الموسمية.

> ليست منصة تبرعات. هي أداة تشخيص + تخطيط مالي للقطاع غير الربحي.

**العرض المباشر:** <https://mousa-alfaify.github.io/Sustainability.associations/>

---

## حالة المشروع الآن

المنصة تعمل على مسارين، يُختار بينهما تلقائيًا حسب وجود إعدادات قاعدة البيانات:

| | **وضع محلي** (بلا إعداد) | **وضع سحابي** (بعد ربط Supabase) |
|---|---|---|
| الدخول | زر دخول تجريبي، بلا كلمة مرور حقيقية | حساب حقيقي (بريد + كلمة مرور)، بريد تأكيد فعلي |
| البيانات | متصفحك فقط (`localStorage`) | قاعدة بيانات Postgres مشتركة |
| متعدد الأجهزة/المستخدمين | ✗ | ✓ — عدة أدوار لنفس الجمعية، متزامن لحظيًا |
| مناسب لـ | تجربة المنصة، عرض توضيحي | الاستخدام الفعلي من فريق حقيقي |

بلا إعداد Supabase يبقى التطبيق قابلًا للاستخدام والعرض بالكامل (هذا مقصود)، لكنه **لا يصلح لإدارة بيانات جمعية حقيقية** لأن البيانات لا تُشارك بين الأجهزة. خطوات التفعيل الكامل في [الإعداد الكامل (الوضع السحابي)](#الإعداد-الكامل-الوضع-السحابي) أدناه — تستغرق حوالي 10 دقائق ولا تحتاج بطاقة دفع.

## التشغيل السريع (وضع محلي، بدون إعداد)

```bash
npm install
npm run dev
```

افتح <http://localhost:3000> — اضغط «دخول إلى لوحة التحكم» مباشرة (بيانات معبّأة مسبقًا). البيانات تُحفظ في متصفحك فقط.

أوامر أخرى:

```bash
npm run build       # بناء إنتاجي عادي
npm run typecheck   # فحص TypeScript
npm run lint        # فحص ESLint
```

## الإعداد الكامل (الوضع السحابي)

يفعّل هذا حسابات حقيقية وقاعدة بيانات مشتركة بين فريقك، مجانًا بالكامل على [Supabase](https://supabase.com) (لا يتطلب بطاقة دفع في الخطة المجانية).

### 1) أنشئ مشروع Supabase

1. سجّل الدخول على [supabase.com](https://supabase.com) → **New Project**.
2. اختر اسمًا وكلمة مرور لقاعدة البيانات (احفظها في مكان آمن) والمنطقة الأقرب لك.
3. انتظر تجهيز المشروع (دقيقة تقريبًا).

### 2) شغّل مخطط قاعدة البيانات

1. من القائمة الجانبية: **SQL Editor** → **New query**.
2. افتح ملف [`supabase/schema.sql`](supabase/schema.sql) من هذا المستودع، انسخ محتواه كاملًا، الصقه، ثم اضغط **Run**.
3. هذا ينشئ الجداول (`organizations`, `organization_members`, `profiles`)، سياسات الأمان (RLS)، ودوال إنشاء/الانضمام للجمعية. تفاصيل كل جزء موثّقة بالعربية داخل الملف نفسه.

### 3) اجلب مفاتيح الاتصال

من **Project Settings → API**:
- **Project URL**
- **anon / public key** (وليس `service_role` — لا تستخدمه هنا أبدًا)

### 4) فعّل الوضع السحابي محليًا

```bash
cp .env.example .env.local
```

افتح `.env.local` واملأ القيمتين:

```
NEXT_PUBLIC_SUPABASE_URL=https://xxxxxxxxxxxx.supabase.co
NEXT_PUBLIC_SUPABASE_ANON_KEY=eyJhbGciOi...
```

```bash
npm run dev
```

أعد تحميل الصفحة — سترى تبويبَي «تسجيل الدخول» و«إنشاء حساب» بدل زر الدخول التجريبي.

### 5) أنشئ أول حساب وأول جمعية (حساب الإدارة الأول)

1. من الموقع: **إنشاء حساب** → اسمك، بريدك، كلمة مرور (6 أحرف فأكثر).
2. Supabase يرسل بريد تأكيد افتراضيًا — افتح الرابط فيه، ثم سجّل الدخول.
3. في شاشة «لنبدأ»: اختر **إنشاء جمعية جديدة**، أدخل اسمها ودورك. أنت الآن أول عضو فيها ومالك بياناتها.
4. من صفحة **الفريق** انسخ **رمز الدعوة** وشاركه مع بقية زملائك (المدير المالي، المدير التنفيذي...) — كل من يدخل الرمز عبر «الانضمام برمز دعوة» يصل لنفس بيانات الجمعية فورًا، من أي جهاز.

> لا يوجد "حساب مدير نظام" منفصل — أول من ينشئ الجمعية هو مالكها، وكل من ينضم لاحقًا عضو كامل الصلاحية في بيانات نفس الجمعية (لا فروقات صلاحيات بين الأدوار حاليًا؛ حقل الدور نصّي للعرض فقط). هذا قرار تبسيط مقصود يناسب فريقًا صغيرًا متعاونًا داخل جمعية واحدة — راجع «قيود معروفة» أدناه إن احتجت صلاحيات متفاوتة لاحقًا.

### 6) فعّل الوضع السحابي على الموقع المنشور (GitHub Pages)

القيمتان أعلاه علنيتان بتصميم Supabase (محميتان بسياسات RLS في قاعدة البيانات لا بالسرية)، لكن يُفضَّل حقنهما وقت البناء بدل كتابتهما مباشرة في الكود:

1. في مستودع GitHub: **Settings → Secrets and variables → Actions → New repository secret**.
2. أضف `SUPABASE_URL` و `SUPABASE_ANON_KEY` بنفس القيمتين.
3. أعد تشغيل آخر عملية نشر (**Actions → أعد التشغيل**) أو ادفع أي commit جديد — سير العمل في `.github/workflows/deploy.yml` يحقنهما تلقائيًا في البناء.

بدون هاتين القيمتين يُبنى الموقع المنشور في الوضع المحلي تلقائيًا (لا ينهار البناء أبدًا).

## أرقام الجمعية التجريبية (جمعية نماء للتنمية)

**المصروف التشغيلي الشهري = 60,000 ر.س**
الرواتب 40,000 · الإيجار 8,000 · التقنية 4,000 · الإدارة 5,000 · أخرى 3,000

**الدخل الحالي**
تبرعات موسمية 450,000/سنة · منح مشاريع 200,000/سنة · عقود خدمات 10,000/شهر · وقف 5,000/شهر
الاحتياطي: 120,000 ر.س

**النتيجة**: إيراد متكرر 15,000 فقط ← فجوة 45,000 ر.س شهريًا، وفترة أمان شهران.

**محفظة الاستدامة المقترحة** (تغلق الفجوة بالكامل):

| المصدر | إضافة شهرية | إجمالي الخط بعد التنفيذ |
|--------|-------------|--------------------------|
| عقود خدمات مع الشركات والجهات الحكومية | +10,000 | 20,000 |
| وقف رقمي واستثمار اجتماعي | +10,000 | 15,000 |
| برامج تدريب ومنتجات معرفية مدفوعة | +10,000 | 10,000 |
| شراكات مسؤولية اجتماعية طويلة المدى | +10,000 | 10,000 |
| توفير من تحسين الكفاءة | 5,000 | — |
| **الإجمالي** | **55,000 إيراد + 5,000 توفير** | **تغطية 60,000 ر.س** |

## المعادلات المالية

| المؤشر | المعادلة |
|--------|----------|
| المصروف التشغيلي الشهري | الرواتب + الإيجارات + التقنية + الإدارة + التسويق + أخرى |
| الإيراد الشهري المتكرر | مجموع المصادر المتكررة فقط (تُستبعد التبرعات الموسمية والمنح المقيدة) |
| الفجوة التشغيلية | الإيراد المتكرر − المصروف التشغيلي |
| فترة الأمان المالي | الاحتياطي النقدي ÷ المصروف التشغيلي الشهري |
| الاعتماد على الموسمية | الدخل الموسمي ÷ إجمالي الدخل |
| العدد الفعّال لمصادر الدخل | 1 ÷ مؤشر هيرفندال (HHI) لتركّز مصادر الدخل |

### مؤشر الاستقلال المالي (0–100)

```
Score = 30 × min(Coverage / 1, 1)
      + 25 × min(EffectiveSources / 5, 1)
      + 25 × min(RunwayMonths / 6, 1)
      + 20 × clamp((0.70 − SeasonalDependency) / (0.70 − 0.20), 0, 1)
```

الأوزان والأهداف المرجعية معرّفة في مكان واحد وقابلة للتعديل:
`lib/finance/independence-score.ts` → `SCORE_WEIGHTS` و `SCORE_TARGETS`.

**التصنيف**: 0–30 خطر مالي مرتفع · 31–50 استقرار ضعيف · 51–70 استقرار متوسط · 71–85 استقرار جيد · 86–100 استدامة مالية قوية.

> ملاحظة منهجية مقصودة: المؤشر يقيس **هيكل** الاعتماد لا **حجم** التمويل، لذلك قد يرتفع شكليًا عند توقف التبرعات الموسمية. مستشار الاستدامة يوضّح ذلك صراحةً في إجابة اختبار الضغط، ولهذا يُقرأ المؤشر دائمًا مع حجم الدخل وفترة الأمان.

### قاعدة بناء المحفظة

1. كل مصدر في الكتالوج يُقيَّم بدرجة ملاءمة (`fitScore`) من ملف الجمعية: الأصول، الخبرات، الشراكات، حجم الفريق، المصادر القائمة.
2. عدد المصادر = بين 3 و5، بحيث **لا يتجاوز أي مصدر جديد 20% من المصروف التشغيلي** (قاعدة التنويع).
3. الفجوة المتبقية (بعد التوفير من الكفاءة) تُوزَّع على المصادر المختارة حسب سعتها النسبية، مقرّبة لأقرب 500 ر.س.

## الوظائف المنفَّذة فعليًا (لا شكليًا)

- **مصادقة حقيقية** (وضع سحابي): تسجيل دخول/خروج فعلي عبر Supabase Auth، تأكيد بريد إلكتروني، رسائل خطأ عربية مطابقة لما يعيده الخادم فعلًا (بيانات خاطئة، بريد مسجّل مسبقًا...).
- **بيانات مشتركة بين الأجهزة والمستخدمين**: ملف الجمعية محفوظ في Postgres، محمي بسياسات RLS تسمح فقط لأعضاء نفس الجمعية بالقراءة والتعديل، ومتزامن لحظيًا (Realtime) — يرى العضو الآخر تعديل زميله دون تحديث الصفحة.
- **انضمام فريق حقيقي**: رمز دعوة فريد لكل جمعية، صفحة «الفريق» تعرض الأعضاء الفعليين وأدوارهم، ومغادرة الجمعية تُلغي الوصول فعليًا (مُختبرة عبر RLS، ليست إخفاء واجهة فقط).
- **حفظ واسترجاع حقيقيان**: التعديل في «ملف الجمعية» يُحفظ (شبكيًا في الوضع السحابي، أو `localStorage` محليًا) ويبقى بعد إغلاق المتصفح وإعادة الفتح — مُختبر يدويًا.
- **تصدير/استيراد فعليان**: زر «تصدير JSON» ينزّل ملف الجمعية الحالي كملف حقيقي؛ «استيراد» يقرأ ملفًا محليًا، يتحقق من بنيته، ويرفض الملفات غير الصالحة برسالة عربية واضحة بدل قبولها بصمت.
- **تأكيد الإجراءات الحساسة**: «إعادة الضبط» و«مغادرة الجمعية» تطلبان تأكيدًا صريحًا في نافذة منبثقة قبل التنفيذ، ولا تُنفَّذان بضغطة واحدة.
- **حالات تحميل/نجاح/خطأ/عدم وجود بيانات حقيقية**: شارة «جارٍ الحفظ… / محفوظ لكل الفريق / تعذّر الحفظ» في الرأس تعكس حالة شبكية فعلية لا نصًا ثابتًا؛ فشل تحميل الجمعية أو الأعضاء يعرض سبب الفشل الفعلي بالعربية.
- **كل المؤشرات المالية** (11 صفحة) دوال خالصة تُعاد حسابها من `profile` الفعلي في كل مرة — لا رقم مخزَّن مسبقًا في أي مكان.
- **أُزيلت 3 تأخيرات وهمية** كانت تحاكي "تحميلًا" غير موجود فعليًا (النتيجة كانت جاهزة أصلًا، والتأخير زخرفة فقط) على أزرار «حلّل جمعيتي» و«ابنِ محفظة الاستدامة» ودخول العرض التجريبي — الآن تكشف النتيجة فورًا بصدق.

## ما لم يُنفَّذ عمدًا (وليس نقصًا سهوًا)

- **لا فروقات صلاحيات بين الأدوار** (مدير الجمعية / المالي / التنفيذي / مسؤول الاستدامة) — كلها أسماء عرض فقط، وأي عضو في الجمعية يملك صلاحية كاملة على بياناتها. الطلب الأصلي لم يحدد صلاحيات متفاوتة بين هذه الأدوار؛ إضافتها تتطلب تصميم مصفوفة صلاحيات لم يُطلب بعد.
- **مستشار الاستدامة محرك قواعد حقيقي، لا نموذج لغوي** — معروض بصدق في الواجهة ("محرك قواعد · جاهز لربط API")، وليس محاكاة تدّعي أنها ذكاء اصطناعي. نقطة الربط الوحيدة الجاهزة لاحقًا: `answerQuestion()` في `lib/advisor/engine.ts`.
- **لا حذف حساب كامل من الواجهة** — حذف حساب مستخدم من Supabase Auth يتطلب صلاحية `service_role` التي لا تُستخدم أبدًا من المتصفح لأسباب أمنية؛ يتم من لوحة تحكم Supabase مباشرة عند الحاجة.

## نتائج الاختبار الفعلي (بيئة هذا الإعداد)

تم تشغيلها فعليًا لا افتراضًا:

- ✅ `npm run typecheck` — لا أخطاء
- ✅ `npm run lint` — لا تحذيرات
- ✅ `npm run build` (وضع Next العادي) و`GITHUB_PAGES=true npm run build` (تصدير ثابت) — كلاهما ينجح، بما في ذلك عند تعريف متغيرات Supabase وهمية وقت البناء (يتحقق أن البناء الثابت لا ينهار بوجودها)
- ✅ الوضع المحلي في متصفح فعلي: تسجيل الدخول → تعديل ملف الجمعية → حفظ → إعادة تحميل الصفحة → البيانات باقية → تنعكس في لوحة التحكم فورًا
- ✅ تصدير JSON: تحقّقت من محتوى الملف الفعلي المُنزَّل (بنية صحيحة، بيانات مطابقة للمعروض)
- ✅ استيراد JSON: ملف صالح يُطبَّق على النموذج، ملف تالف (`JSON` غير صحيح) يُرفض برسالة عربية
- ✅ نافذة تأكيد «إعادة الضبط»: الإلغاء لا يغيّر البيانات، التأكيد يستبدلها
- ✅ زر «حلّل جمعيتي» و«ابنِ محفظة الاستدامة»: يكشفان النتيجة فورًا بلا مؤشر تحميل وهمي
- ✅ نموذج إنشاء الحساب السحابي (بمتغيرات Supabase وهمية لاختبار مسار الخطأ فقط): استدعاء شبكي حقيقي يفشل برسالة عربية صريحة ("تعذّر الاتصال بالخادم...") بدل نجاح مزيَّف
- ⚠️ **لم يُختبر مع مشروع Supabase حقيقي** — لا يوجد لديّ حساب Supabase لإنشاء مشروع فعلي، فتعذّر اختبار: التسجيل الفعلي، تأكيد البريد، إنشاء/الانضمام لجمعية، التزامن اللحظي بين جلستين، وسياسات RLS على بيانات حقيقية. الكود واتصالاته الشبكية حقيقية ومبنية على واجهة Supabase الموثّقة رسميًا، لكن التحقق من مشروع فعلي متبقٍ لك بعد إكمال [الإعداد الكامل](#الإعداد-الكامل-الوضع-السحابي) أعلاه — إن ظهرت أي رسالة خطأ غير متوقعة أثناء ذلك أرسلها لي وسأصلحها فورًا.
- ✗ لم يُختبر على أجهزة/متصفحات فعلية متعددة لنفس الجمعية (يتطلب مشروع Supabase حقيقي أعلاه)
- ✗ لم يُختبر بصريًا على شاشة جوال حقيقية في هذه الجلسة (التصميم Responsive بنفس فئات Tailwind المستخدمة في كل الصفحات سابقًا ولم تتغير، لكن لم أُعد فتح كل صفحة بعرض جوال بعد هذا التعديل تحديدًا)

## النشر

يُنشر الموقع تلقائيًا على GitHub Pages عند كل دفع إلى الفرع `main` عبر سير العمل في [`.github/workflows/deploy.yml`](.github/workflows/deploy.yml) — يبني، يفحص الأنواع، ثم يدفع مخرجات `out/` إلى فرع `gh-pages`.

- بدون أسرار `SUPABASE_URL` / `SUPABASE_ANON_KEY` في إعدادات المستودع → الموقع المنشور يعمل في الوضع المحلي.
- بعد إضافتهما (خطوة 6 في [الإعداد الكامل](#الإعداد-الكامل-الوضع-السحابي)) → الموقع المنشور نفسه يعمل بالوضع السحابي الكامل، بلا أي تعديل كود إضافي.

للبناء المحلي بنفس طريقة النشر:

```bash
GITHUB_PAGES=true npm run build   # المخرجات في out/
```

لتغيير اسم المستودع لاحقًا، عدّل قيمة `repository` في `next.config.mjs`.

## قيود معروفة ومتطلبات خارجية متبقية

1. **يحتاج مشروع Supabase فعلي للاستخدام الجماعي الحقيقي** — الخطوات جاهزة أعلاه، ينقصها فقط إنشاء الحساب من جهتك (مجاني).
2. **لا صلاحيات متفاوتة بين الأدوار** — أي عضو في الجمعية يعدّل كل شيء (راجع «ما لم يُنفَّذ عمدًا» أعلاه).
3. **حذف حساب المستخدم بالكامل** يتم من لوحة Supabase مباشرة، وليس من داخل المنصة.
4. **رسائل تأكيد البريد الإلكتروني** تُرسل عبر خادم بريد Supabase الافتراضي (محدود العدد يوميًا في الخطة المجانية) — يكفي لفريق صغير؛ لحجم أكبر يلزم ربط مزوّد بريد خاص من إعدادات Supabase (خطوة خارج نطاق هذا المستودع).
5. **الوضع السحابي غير مُختبَر على مشروع Supabase حقيقي بعد** (راجع «نتائج الاختبار الفعلي» أعلاه) — الكود جاهز ومبني على التوثيق الرسمي، والتحقق النهائي يحتاج منك إكمال الإعداد مرة واحدة.
